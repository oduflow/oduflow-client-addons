# Руководство администратора OduMCP

## Роли безопасности

- **MCP Auditor** может просматривать профили, одобрения и записи аудита.
- **MCP Manager** может настраивать профили, включать пользователей и решать
  судьбу одобрений.

Не используйте учётную запись администратора как MCP-пользователя. Права
доступа Odoo, record rules, разрешённые компании и MCP-профиль действуют
совместно: профиль способен только сузить то, что назначенному пользователю
Odoo и так разрешено.

## Включение MCP для пользователя

1. Откройте **Settings > Users & Companies > Users** и выберите пользователя.
2. Перейдите на существующую вкладку **Account Security**.
3. Включите **MCP Active**.
4. Выберите **Profile**.
5. Сохраните пользователя.

Сохранение этих полей не создаёт постоянный API-ключ. При запуске каждой беседы
OduPilot проверяет пользователя, галочку и профиль и выпускает собственный
подписанный токен сессии, который отзывается при закрытии беседы. Для подключения
внешнего MCP-клиента пользователь создаёт личный ключ в разделе **Настройки →
Безопасность учётной записи**, где секрет показывают один раз. Такой ключ
работает на MCP-эндпоинтах и больше нигде, а обычный ключ **All APIs** ими
отвергается.

Отдельной записи User Access и отдельного меню нет. У каждого пользователя
ровно один флаг MCP и один профиль прямо на нём. Счётчики использования на
пользователе не хранятся: минутная и суточная квоты считаются по неизменяемым
записям аудита.

**MCP Active** и **Profile** — намеренно два поля. Профиль говорит, что
пользователю можно делать; галочка — можно ли ему вообще что-нибудь. По
умолчанию галочка снята, поэтому один только профиль ничего не открывает:
профиль, пришедший из шаблона пользователя или из копии, сам по себе доступа не
даёт. Обратная комбинация запрещена: при включении галочки без профиля
появляется ошибка **Select an MCP profile before enabling MCP access**.

## Настройка профиля безопасности

Откройте **MCP > Security Profiles**. Профиль работает по принципу
default-deny: без явной Model Policy и без более широкого доступа по умолчанию
не открыто ничего.

При установке модуля создаются два профиля. **Administrator** (код `admin`)
читает, изменяет и создаёт в любой модели, которой его пользователь-коннектор
и так уже пользуется, через доступ по умолчанию, а не через Model Policies.
Удаление, отчёты, автоматическое одобрение и частичное чтение полей остаются
выключенными. **Read Only** (код `readonly`) только читает и агрегирует. Никому
они не назначены: сам по себе профиль ничего не открывает, пока пользователь не
получит **MCP Active** и этот профиль. Обновления их не перезаписывают, поэтому
ужесточать профиль безопасно; если клиенту нужен другой объём прав, скопируйте его.

### Профиль и лимиты

- **Allowed Companies** пересекается с компаниями пользователя-коннектора.
  Пустой список означает все компании, которые у пользователя уже есть.
  Отсутствие пересечения — это ошибка, а не молчаливый полный доступ.
- **Max Records Per Call** ограничивает результаты поиска, чтения, агрегации и
  отчётов.
- **Max Batch Size** ограничивает, сколько записей может затронуть один план
  создания, изменения или удаления.
- **Rate Limit Per Minute** и **Daily Quota** считаются по строкам аудита.
  Нулевая суточная квота отключает суточную проверку; граница суток — UTC.
- **Approval TTL Minutes** — сколько времени план изменения остаётся
  исполнимым.

### Доступ к моделям по умолчанию

Это резервный режим, применяемый только к моделям без явной Model Policy.

- **Explicit policies only** — рекомендуемое значение по умолчанию. Ничего вне
  вкладки Model Policies недостижимо.
- **Read any accessible model** — чтение и, если включён **Aggregate**,
  агрегация любой нетранзиентной модели, которую пользователь Odoo может
  читать.
- **Read and update any accessible model** — дополнительно разрешает изменения.

**Create on Any Accessible Model** и **Delete from Any Accessible Model**
добавляют в тот же резервный режим ещё две операции. Все они по-прежнему
требуют соответствующего права доступа у пользователя-коннектора, и каждое
изменение всё так же проходит через одобрение.

В резервном режиме поля, чьи имена похожи на секреты (`password`, `pass`,
`token`, `api_key`, `secret`, `private`, `credential`, `authorization`), и все
бинарные поля скрыты, а запись дополнительно ограничена нередактируемыми только
на чтение и нетехническими полями.

Системные параметры (`ir.config_parameter`) подчиняются обычным политикам моделей и
общему доступу профиля с учётом прав пользователя подключения в Odoo. Для
ограниченного чтения добавьте явную Model Policy только с разрешением Read,
выберите `key` и `value` как читаемые поля и задайте обязательный домен, например
`[["key", "=like", "oduflow.%"]]`. Он выбирает ключи, начинающиеся с
`oduflow.`; используйте `oduflow%` для всех ключей, начинающихся с `oduflow`.
Значения параметров могут содержать учётные данные; фильтрация по именам полей не распознаёт
секреты в универсальном поле `value`.

Резервный режим никогда не покрывает:

- транзиентные модели (визарды);
- `res.users.apikeys` и сами модели OduMCP — их
  нельзя открыть вообще, даже явной политикой.

На моделях безопасности резервный режим работает только на чтение, в любом
варианте:

- `base.automation`, `ir.actions.server`, `ir.cron`, `ir.mail_server`,
  `ir.model.access`, `ir.rule`, `ir.ui.view`, `res.groups` — чтение лишь
  сообщает правила, под которыми коннектор и так работает, тогда как запись в них
  обошла бы этот слой политик; явная Model Policy всё ещё может открыть их
  осознанно на запись;
- `res.users` — модель читается, но никогда не создаётся, не изменяется и не
  удаляется, потому что это меняет членство в группах.

Для чтения по-прежнему нужно соответствующее право доступа Odoo у
пользователя-коннектора: `ir.model.access` и `ir.rule` доступны только
менеджерам прав доступа, а `ir.ui.view`, `ir.cron`, `ir.mail_server`,
`base.automation` и `ir.actions.server` — пользователям Настроек.

### Возможности

Каждая возможность включает или выключает одну конкретную операцию. Сами по
себе они ничего не добавляют — политики моделей и полей действуют поверх.

| Возможность | Что на самом деле разрешает |
| --- | --- |
| **Schema** | Описание полей модели. Список разрешённых моделей доступен всегда. |
| **Aggregate** | Сгруппированную агрегацию. Политика модели может отключить её для одной модели. |
| **Reports** | Отрисовку PDF-отчёта не более чем для 20 записей, если профиль может читать модель отчёта. |
| **Attachments** | Скачивание вложения читаемой записи и загрузку вложения к записи, доступной на запись. |
| **Chatter** | Публикацию сообщения в чаттере записи, доступной профилю на запись, у модели с чаттером. |
| **Activities** | Полное управление своими активностями коннектора: постановку, чтение, правку и закрытие. См. ниже. |
| **Auto Approve Low Risk** | Создание планов сообщений в чаттере и активностей сразу одобренными. |
| **Partial Field Reads** | Ответ на чтение доступными колонками вместо отказа, когда список полей называет и поле, которое профиль не открывает. |

Три из них уже, чем кажется по названию:

- **Activities** ограничен владением, а не моделью. Он открывает
  `mail.activity` только для активностей, которые пользователь-коннектор создал
  или которые назначены на него, — ровно то определение, что используется в
  правиле ядра `mail_activity_rule_user`. Активности коллег на тех же записях
  остаются невидимыми.
- **Auto Approve Low Risk** — это не «одобрять всё безобидное на вид». План
  одобряется автоматически, только если его вычисленный риск низкий **и** его
  действие — сообщение в чаттере или постановка активности. Уровни риска
  зашиты в коде: создание, изменение и загрузка вложения — средний, удаление —
  высокий, чаттер и активность — низкий, а вызов метода берёт уровень риска из
  своей Method Policy. Автоодобрение методов отдельно регулирует **Require Human Approval**.

- **Partial Field Reads** срезает только обычный список полей. Закрытое поле в
  домене поиска или в сортировке по-прежнему приводит к отказу: его пропуск
  вернул бы другой набор записей, а не те же записи с меньшим числом колонок;
  запись не срезается никогда. Чтение, где закрыты все поля, тоже отклоняется,
  поэтому клиент никогда не получает пустой успех. В ответе приходит блок
  `omitted_fields` с именами пропущенных полей.

  Оставьте выключенным для профиля, чьи allowlist-ы и есть настоящий контроль
  доступа: клиент, получивший данные вместе с примечанием, может сообщить
  закрытое поле как пустое, а не как недоступное. Включайте для широкого
  внутреннего профиля, где сэкономленный вызов дороже строгого отказа.

Автоодобрение убирает только клик человека. Клиенту всё равно нужно сделать
предпросмотр, а затем исполнение, и оба шага попадают в аудит.

#### Что открывает Activities

При включённой возможности — и если явная Model Policy на `mail.activity` её не
перекрывает — профиль даёт пользователю-коннектору:

| Операция | Разрешена | Как |
| --- | --- | --- |
| Чтение | да | `records.search`, `records.read`, `records.count` и агрегация при включённом **Aggregate** |
| Создание | через запись-хозяина | `activity.schedule`, требующий права записи на запись, к которой привязывается активность |
| Изменение | да | `activity.update` по `activity_type_id`, `summary`, `note`, `date_deadline`, `user_id` |
| Закрытие | да | `activity.done`, помещающий отчёт в чаттер записи |
| Удаление | никогда | `record.delete` по `mail.activity` отклоняется, действия отмены нет |

В Odoo 19 `activity.done` использует `_action_done`, чтобы опубликовать отчёт и завершить дело. Завершённые дела могут архивироваться. Прямое удаление через MCP остаётся запрещённым, чтобы завершение сохраняло след аудита.

Два поля намеренно недоступны на запись: `res_model` и `res_id`. Перенос
активности на другую запись привязал бы её к записи, которую профиль трогать не
вправе, поэтому перепривязка отклоняется с `field_denied`.

Прямой `record.create` по `mail.activity` отклоняется по той же причине:
`activity.schedule` проверяет право записи на модель-хозяина, а голое создание
этого не сделает.

Явная Model Policy на `mail.activity` по-прежнему перекрывает всё
вышеперечисленное — используйте её, когда профилю действительно нужна другая
область, включая удаление.

### Политики моделей

Вкладка **Model Policies** нужна для правил и исключений по конкретным моделям.
Для каждой модели можно задать:

- разрешённые операции: чтение, агрегацию, создание, изменение, удаление;
- **Readable Fields** и **Writable Fields** — независимые списки разрешений. Пустой
  список разрешает все поля для соответствующей операции; заполненный — только
  выбранные поля. `id` и `display_name` остаются читаемыми. Права Odoo, поля только
  для чтения и отдельные разрешения на бинарные поля продолжают действовать;
- **Allow Binary Read/Write**, чтобы включить в эти списки бинарные поля;
- **Forced Domain** — JSON-домен Odoo, который добавляется через AND к каждому
  поиску и проверяется повторно после изменения, чтобы изменение не вывело
  запись за пределы области;
- **Max Records**, который может только понизить лимит профиля.

Чувствительные к безопасности модели OduMCP и модели учётных данных здесь
тоже отклоняются.

### Разрешённые методы

Вкладка **Allowed Methods** — единственный способ разрешить клиенту вызов
бизнес-метода. По умолчанию не вызывается ничего, приватные методы отклоняются
всегда. В записи задаются модель, имя метода, уровень риска, сколько записей он
может получить, можно ли вызывать его без id записей, разрешены ли позиционные
аргументы, точный список допустимых именованных аргументов и максимальный
размер аргументов.

Укажите точное имя в **Method Name** или `*`, чтобы разрешить все публичные
бизнес-методы этой модели. Активная политика с точным именем имеет приоритет над `*`;
её настройки полностью заменяют настройки wildcard. Неактивные записи
игнорируются. Шаблоны вроде `action_*` не поддерживаются.

**Require Human Approval** включён по умолчанию. Отключите его в выбранной
политике для автоматического одобрения допустимых планов независимо от уровня риска.
Предпросмотр, выполнение и аудит сохраняются. Политики wildcard сохраняют те же
лимиты записей и аргументов; пустой список именованных аргументов по-прежнему
запрещает их, а вызов без id записей требует **Allow Model Method**.

Приватные методы (включая помеченные как приватные для RPC) и общие методы
ORM/веб-фреймворка недоступны даже при точной политике. Используйте отдельные
операции MCP для CRUD, поиска и агрегации, чтобы действовали проверки операций,
полей и доменов. Действия архивации и разархивации остаются доступны. Бизнес-методы
могут менять данные внутри себя; политика модели только для чтения не делает
разрешённый бизнес-метод доступным только для чтения. По умолчанию политики wildcard не включены.

### Пользователи

Вкладка **Users** назначает профиль пользователям напрямую и зеркалит поле с
формы пользователя.

## Проверка изменений

Ответы предпросмотра и статуса содержат `approval_url`, чтобы агент мог направить
согласующего прямо к плану. Ссылка использует настройку `web.base.url`;
укажите в ней публичный HTTPS-адрес. Она не содержит токена доступа
и требует обычного входа в Odoo и прав MCP-менеджера для одобрения.

Откройте **MCP > Approval Inbox**. Список сгруппирован по полю
**Request**: все планы, которые клиент создал для одной задачи, несут одно и то
же обозначение запроса, поэтому задача на сто записей проверяется и решается
одной группой. Отметьте планы — или флажок в шапке после раскрытия группы — и
нажмите **Approve Selected**, **Reject Selected** или **Delete Selected
Expired**. Окно подтверждения показывает, что будет обработано и сколько
выбранных записей пропущено, потому что их состояние не подходит действию.

Перед одобрением изучите
обезличенный diff, целевую модель, риск, срок истечения, пользователя и
профиль. Записи одобрений неизменяемы; после отклонения или истечения клиенту
нужно создать новый план. Одобренный план исполняется только один раз и только
до истечения срока.

Вкладки **Redacted Diff**, **Result** и **Integrity** показывают сохранённые
снимки подсвеченным YAML вместо сырого JSON; на **Integrity** дополнительно
виден отправленный payload, а все обезличенные значения выделены красным.
Включите режим разработчика, чтобы увидеть рядом с каждым блоком исходный
JSON — например, чтобы скопировать его в тикет.

Сохранённый payload хешируется. Если на момент исполнения он не совпадает со
своим хешем, план завершается ошибкой вместо запуска.

## Аудит и квоты

Откройте **MCP > Audit Log**, чтобы изучить исходы запросов.
Логируется каждый запрос — и успешный, и отклонённый, и ошибочный — с
операцией, моделью, id затронутых записей, кодом статуса, кодом ошибки,
длительностью, удалённым адресом и user agent. Само тело запроса не
сохраняется: только его хеш и короткая сводка. Частичное чтение дополнительно
записывает пропущенные поля, поэтому запрос, зачтённый как успех, всё равно
показывает работу политики. Строки аудита неизменяемы и
питают проверки минутной и суточной квот. Записи пользователей не дублируют
итоги по запросам, отказам и времени последнего использования. **Target
Records** перечисляет затронутые id в виде YAML, исходный JSON остаётся в
режиме разработчика.

## Глобальные настройки

В **Settings > MCP** включается и выключается control API и задаются
лимиты payload, бинарных данных, хранения, группировки запросов и
event-тикетов. Отключение API
оставляет все пользовательские MCP-настройки нетронутыми и заставляет любую
аутентифицированную операцию возвращать `service_disabled`.

**Request Grouping Window (minutes)** определяет, как группируются планы без
явного ключа партии. Планы одного пользователя коннектора и профиля
присоединяются к последнему запросу, пока между ними проходит меньше указанного
числа минут; по умолчанию — 10. Ноль помещает каждый план в собственный запрос.
На клиента, который передаёт ключ партии, эта настройка не влияет.

Хранение обеспечивает autovacuum Odoo: строки аудита старше окна хранения
аудита и завершённые одобрения старше окна хранения одобрений удаляются, а
просроченные планы помечаются истёкшими. Ничто другое эти строки удалить не
может.

## Отключение доступа

Снимите **MCP Active**, чтобы остановить доступ без удаления профиля.
Пользователь с сохранённым профилем и снятой галочкой — штатное состояние
приостановки, и вернуть доступ можно одной галочкой. Это лучше остальных
вариантов: очистка профиля теряет запись о том, какой профиль был выдан,
архивация профиля останавливает всех, кто его использует, а архивация
пользователя закрывает ему Odoo целиком. Личные ключи не трогаются: это его
собственные учётные данные, а снятая галочка их и так не принимает. При
компрометации отзовите такие ключи во вкладке пользователя **Account
Security**. Существующие токены сессий OduPilot отвергаются сразу. Любое из этих действий также обесценивает выданные
event-тикеты.

Удаление пользователя со вкладки **Users** профиля — тот же отзыв доступа с
другой стороны: профиль и галочка снимаются вместе.

## Когда клиент сообщает об отсутствии доступа

Вызывающий без MCP-доступа получает `403` от `/odumcp/v1/*` с одним из
двух кодов: `mcp_access_not_configured`, если профиль не выбран, и
`inactive_mcp_access`, если неактивны пользователь Odoo, галочка или профиль.
MCP-сервер отдаёт своему клиенту в обоих случаях `401`, и такой клиент,
например OpenCode, вообще не показывает инструмент Odoo. В чате это выглядит
как отсутствующий MCP-сервер, хотя сервер отказывает конкретному пользователю,
поэтому сначала проверьте оба поля у пользователя, а уже потом сервер и
подписанный токен сессии. Постоянный ключ в **Account Security** для OduPilot не
нужен: для каждой беседы он создаёт и отзывает отдельный ключ.


## Развёртывание на Odoo 19

Установите `odumcp` из `addons`; используйте Oduflow или прилагаемый MCP-сервер. Адрес событий `/odumcp/v1/events` использует аутентифицированный короткий опрос; сервер ждёт одну секунду после пустого ответа. Для личных API-ключей нужны допустимые сроки действия Odoo 19. Этот порт не переносит базу Odoo 15.

## Идентификатор установки

Установите `odumcp` как новый модуль. Он использует модели и настройки `odumcp.*`, API-маршруты `/odumcp/v1/`, пакет Python `odumcp_server` и серверные переменные `ODUMCP_*`. Миграция предыдущей установки не предусмотрена. Удалите предыдущий модуль перед развёртыванием этого кода; при удалении также удаляются зависимые модули и их данные. Затем установите необходимые зависимые модули заново. Перед использованием примера Compose соберите переименованный серверный образ локально (`docker compose -f docker-compose.example.yml up --build -d`); публикация образа выполняется отдельно.

## Интеграция с production Oduflow

Oduflow может обращаться к модулю напрямую; отдельный MCP-сервер необязателен.
При создании production на Odoo 19 Oduflow устанавливает модуль и регистрирует
ключ из своей конфигурации как API-ключ администратора только для MCP.
Управляемый ключ называется **Oduflow production (managed)**. Odoo хранит только
хеш ключа; его открытое значение остаётся в конфигурации Oduflow.

Локальная операция настройки заменяет только управляемый ключ. Личные API-ключи
остаются действительными. Существующие MCP-профили, политики и приостановленный
доступ не меняются. Если у администратора нет профиля, создаётся профиль только
для чтения; перед использованием планов изменений явно настройте права записи.

После изменения production-ключа и перезапуска Oduflow используйте
`sync_production_mcp` для синхронизации одного или всех production команды.
Проверьте каждый результат и повторите неудачные операции после восстановления
или запуска окружений. Ротация выполняется отдельно в каждой базе; до успешной
синхронизации старый ключ остаётся действительным. Восстановление резервной копии
может вернуть старый ключ, поэтому после него также нужна синхронизация. Удаление
ключа из Oduflow не отзывает его в Odoo; при отключении интеграции удалите
управляемый API-ключ.

Запросы с управляемым ключом записывают `source = oduflow` в журнал аудита.
Это признак ключа, а не конкретного человека или подтверждённого сетевого
источника; он не отменяет политики. Согласование бизнес-изменений остаётся в Odoo,
а инфраструктурные операции production отдельно авторизует Oduflow.

## Обновление объединённого модуля

Версия `19.0.1.4.0` объединяет платформенный и клиентский модули. Обновляйте `odumcp` на месте, сохраняя существующие записи, профили, одобрения и журнал аудита. Встроенный `deploy/odumcp_server` остаётся доступным. Приложение теперь называется **MCP**.

Перед обновлением проверьте существующие политики моделей: пустой список полей чтения или записи теперь разрешает все остальные допустимые поля этой операции. Заполните списки, чтобы сохранить узкий набор полей. Права операций, ACL Odoo, принудительные домены и ограничения бинарных полей продолжают действовать.

Установка управляемого ключа требует окружения суперпользователя. Она распознаёт `Oduflow production` и `Oduflow production (managed)` как имена управляемых MCP-ключей администратора. При следующем вызове эти записи заменяются одним каноническим ключом `Oduflow production (managed)`. Личные ключи и ключи с другой областью действия не затрагиваются. Повторная установка того же бессрочного канонического ключа сохраняет его запись. Существующие профили и приостановленный доступ сохраняются. Аудит определяет оба управляемых имени как `source = oduflow` ещё до повторной установки.
