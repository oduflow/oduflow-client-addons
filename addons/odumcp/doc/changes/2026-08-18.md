# 2026-08-18

## Why MCP Active exists next to Profile

- The administrator guide now explains the two fields: the profile states what a
  user may do, the flag states whether that user may do anything at all.
- The flag stays off until it is enabled by hand, so a profile that arrives from
  a user template grants nothing on its own.
- Clearing the flag while keeping the profile is documented as the supported way
  to suspend one person, instead of clearing the profile or archiving the user.

## Reading a refused MCP request

- A new section describes what a refused caller sees: `403` with
  `mcp_access_not_configured` when no profile is selected and
  `inactive_mcp_access` when the user, the flag or the profile is inactive.
- The MCP server reports both as `401`, so a client offers no Odoo tool at all
  and the failure looks like a missing server rather than a refused user.

## The MCP key follows the access

- Enabling **MCP Active** for a user now issues an MCP-only API key named
  **MCP access** and selects it as the OduPilot default, so a chat user no longer
  has to create one by hand before the Odoo tool appears.
- Clearing the flag deletes that key again. Keys the user created personally are
  kept, because the cleared flag already refuses them.
- Removing a user from a profile's **Users** tab now clears the flag as well,
  which previously refused to save at all.
- Existing users with the flag already enabled receive the key on upgrade.

## Change plans are shown as highlighted YAML

- **Redacted Diff** and **Result** in the Approval Inbox now render the stored
  snapshot as highlighted YAML instead of a single line of raw JSON.
- **Integrity** additionally shows the submitted payload for MCP managers, with
  redacted values marked in red.
- The Audit Log form shows affected ids in a **Target Records** block, also as
  YAML.
- The raw JSON of every block remains available in developer mode.

## Guides now describe every profile capability

- The User Guide lists what a connector can actually do, explains the
  preview/approve/execute round trip, idempotency keys, plan expiry, live
  resource updates, and the MCP keys a user sees, and covers more error codes.
- The Administrator Guide documents profile limits, the Default Model Access
  fallback with its safety denylists, every capability switch, Model Policies,
  Allowed Methods, audit content, retention, and global settings.
- **Activities** is documented as what it is: permission to *schedule* an
  activity on a writable record, not CRUD on `mail.activity`.
- **Auto Approve Low Risk** is documented as applying only to chatter messages
  and scheduled activities, and only to the manual approval step.
