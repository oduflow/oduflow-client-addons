# 2026-08-17

## Workspace files removed with the session record

- Deleting a technical AI session record now removes its workspace directory,
  including every attachment and Markdown conversion. Previously only closing
  the chat did that, and a deleted record left its files behind forever.
- The cleanup command survives the deleted record and carries everything the
  bridge needs. A session whose files were already removed on close is not
  cleaned up twice.
- Daily retention drops those finished cleanup commands once they are older
  than the event retention period.

## Readable document attachments

- Word, PowerPoint, Excel, OpenDocument, RTF, EPUB, CSV and PDF attachments are
  now converted to Markdown by AnyDoc and stored next to the original as
  `<file>.md`, so AI reads the content instead of a binary file.
- The prompt lists the conversions that were produced, and AI is instructed to
  use them. Attachments of other types, such as images, are unchanged.
- Conversion runs in the bridge and needs no Bash, so it also works in profiles
  where Bash is denied. The `anydoc` command is additionally available in the
  OpenCode container for profiles that allow Bash.
- AnyDoc does no text recognition: a scanned or image-only PDF produces no
  Markdown and is reported as unreadable.

## Clickable record mentions

- Every mention of an Odoo record in an AI answer now opens its form: a record
  ID in a result table, but also a task named by its title, a stage, a project
  or a customer mentioned in ordinary text.
- Only records the AI actually read through a tool are linked, so a link never
  leads to a guessed record. Counts and filtered lists such as "55 tasks in New"
  stay plain text.
- Odoo builds the address from its own web base URL; the AI only marks which
  model and ID a mention belongs to.

## Visible provider retries

- When the AI provider keeps retrying a request — for example after the
  subscription usage limit is reached — the conversation now receives a notice
  with the reason instead of staying silently on **AI is responding…**.
- One notice is posted per reason: identical attempts stay quiet, a different
  reason posts a new notice, and a finished answer resets the state.

## Least-privilege bridge account

- The bridge RPC endpoints now require the new **OduPilot Bridge Service** group
  instead of system-administrator rights, so the bridge account no longer needs
  access to anything outside AI chat.
- System administrators no longer pass the bridge gate implicitly; the group has
  to be assigned deliberately.
- Upgrading converts an account whose login is `odupilot-bridge`: it receives the
  new group and loses every other explicitly assigned group. A bridge account
  with a different login still has to be converted by hand, otherwise it cannot
  claim commands and its heartbeat stays missing.

## New chat access

- Internal users can start **New OduPilot** without Settings access. The server
  action now declares the same internal-user group as its Discuss menu item.

## Readable AI responses

- Added full CommonMark rendering for AI responses, including headings, lists,
  links, fenced code, strikethrough and URL linkification.
- Converted Markdown tables into responsive HTML tables.
- Added server-side sanitization that removes scripts and unsafe attributes
  before an AI response is stored as a message.
- Pinned the Markdown renderer in the production Odoo image requirements.

## Event-driven bridge commands

- Replaced one-second XML-RPC command polling with Odoo longpolling wake-ups.
- Kept durable command claiming, FIFO ordering, retries and periodic
  reconciliation in the transactional outbox.
- Bus notifications contain no command payloads, attachments or credentials.
- Fixed the OpenCode workspace root at `/workspace` and removed its Odoo
  setting and environment-variable override.

## Recovery from stuck requests

- Added a configurable timeout and automatic watchdog for sessions that remain
  busy after a model, OpenCode or network failure.
- The watchdog cancels queued follow-up prompts, records the failure, notifies
  the conversation and sends an idempotent abort so the session becomes usable
  again without manual database changes.
- Chaos acceptance confirmed bridge backfill without duplicates. An OpenCode
  process crash during an active provider stream is recovered by the watchdog.
- Interrupted requests without tool or permission activity are replayed
  automatically once. Tool activity and repeated failures now produce a
  synchronized **Retry** / **Dismiss** recovery card in Discuss.
- A late final backfill cancels still-pending recovery commands, preventing a
  duplicate replay after the original answer has already arrived.
- Completed or superseded assistant streams now remove their transient Discuss
  message even when delayed crash-recovery events arrive out of order.

## Resilient event stream

- A single malformed event no longer drops the whole OpenCode event stream. Text
  containing a Unicode line separator used to split one event in two and end the
  connection, so the conversation stayed on **AI is responding…** until the
  busy-session watchdog released it half an hour later.
- After every reconnection the bridge compares busy sessions with the sessions
  OpenCode is actually running and immediately releases the ones whose
  completion event was lost, instead of waiting for the watchdog.

## Permission cards in Discuss

- Added inline cards for OpenCode permission requests with **Allow once**,
  **Always** and **Reject** actions.
- Permission answers are delivered through the durable outbox and synchronized
  to every conversation participant through Odoo longpolling.
- Answered and expired cards remain visible with their final status and actor;
  duplicate clicks and repeated events cannot create duplicate replies.

## Live AI responses

- Added real-time assistant text updates in Discuss through the existing Odoo
  longpolling connection.
- The browser updates one escaped transient message while generation is active,
  then replaces it with the stored Markdown response without duplicates.
- Abort, failure, watchdog recovery and session close remove stale live output.

## Retention and monitoring

- Added configurable daily cleanup for raw audit events and closed technical
  session records while preserving Discuss channels and messages.
- Added a dedicated runtime dashboard with bridge/OpenCode heartbeat, health
  latency, queue and stuck-command counts, errors and 24-hour durations.
- Added searchable command history with completion timestamps and durations.

## Developer environment delivery

- Added automatic developer environment bootstrap through a selected full MCP
  server and persisted its validated HTTPS URL on the chat session.
- Added a protected publish outbox command that rejects dirty or unsafe
  worktrees, pushes the generated branch and creates or updates its GitHub pull
  request without exposing the profile PAT to the model.

## Live session status in Discuss

- Added a compact status bar above each AI conversation for initialization,
  readiness, active work, permission waiting, errors and closure.
- Session transitions update through the existing Odoo longpolling connection;
  Discuss does not poll the session model.
- Error states include a bounded summary so users can identify the failure
  without leaving the conversation.
- AI conversations are now Discuss-only and no longer reappear as docked chat
  windows over the main application menu.

## Reliable development responses

- Prevented an OpenCode turn from repeating indefinitely after the model had
  already returned `finish=stop` by leaving message ID generation to OpenCode.
- Preserved retry idempotency with a stable prompt-part ID and history check.

## Personal Odoo MCP identity

- Users can select one personal MCP-only API key as the default identity for
  newly created OduPilot sessions.
- Each chat receives a separate temporary Odoo MCP key, exposed to OpenCode as
  `ODOO_API_KEY` and revoked when the chat closes.
- Remote MCP headers can use `Bearer {env:ODOO_API_KEY}` without storing the
  user's key in the MCP server record; `${ODOO_API_KEY}` is not supported by
  OpenCode JSON configuration.

## Profile-based LiteLLM credentials

- OduPilot profile assignment now appears on the user's **Account Security**
  tab instead of **Preferences**.
- Each profile now has a read-only **Users** tab showing its active and archived
  assigned users, their logins, companies and active status.
- The LiteLLM API key is configured once on the OduPilot profile and shared by
  the users assigned to that profile.
- Existing user keys are migrated to their profiles; profiles are split when
  assigned users previously had different keys.
