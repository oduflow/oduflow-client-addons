# Руководство администратора Oduscale

Oduscale управляет доступом на существующем сервере Headscale. Разверните сервер
управления, политику VPN и шлюз Odoo отдельно до подключения сотрудников.

## Установка и назначение прав

Добавьте каталог `addons/` репозитория в `addons_path` и установите `oduscale`.
Зависимости: `hr`, `mail` и пакет Python `requests`. Установите `odubook`, чтобы
читать эту документацию в Odoo; для управления VPN он необязателен.

Выдайте ответственным пользователям право **Oduscale / Manage employee VPN access**.
Эта роль также включает права сотрудника отдела кадров. Администраторы настроек
наследуют роль Oduscale. Ответственные могут управлять доступом сотрудников и читать
конфигурацию серверов; только администраторы настроек могут создавать и изменять
серверы и видеть имя переменной API-ключа. Правила компаний ограничивают серверы,
подключения, устройства и историю ключей разрешёнными пользователю компаниями.
Сотрудник и сервер в записи доступа должны относиться к совместимым компаниям.

## Настройка сервера Headscale

Откройте **Oduscale → Headscale Servers**, создайте сервер и заполните поля:

| Поле | Назначение |
| --- | --- |
| Name / Company | Название сервера и компания-владелец. |
| API URL | Адрес Headscale, доступный из Odoo, без `/api/v1`. |
| API Key Env | Переменная окружения с API-токеном; по умолчанию `ODUSCALE_API_KEY`. |
| Login URL | Публичный HTTPS-адрес сервера управления, доступный клиентам Tailscale. |
| Odoo URL | Необязательный адрес Odoo, доступный через VPN-шлюз. |
| Key Lifetime Minutes | Срок одноразового ключа: 5–1440 минут; по умолчанию 60. |

Адреса должны использовать HTTP(S) и не содержать учётных данных, строки запроса
или фрагмента. Адрес подключения требует HTTPS. Поместите API-токен в окружение
процесса Odoo, а не в запись сервера; для разных серверов используйте разные имена
переменных. Нажмите **Test connection**, чтобы проверить доступ к API пользователей
Headscale. Это не проверяет клиентский маршрут VPN или шлюз Odoo.

## Эксплуатация и восстановление

- Запланированное действие **Oduscale: synchronize employee devices** выполняется
  каждые 5 минут от системного пользователя. Убедитесь, что обработка cron Odoo включена.
- Проверяйте **Last Sync** и **Last Error** на сервере. Обработанная ошибка синхронизации
  сохраняется; успешная синхронизация сервера очищает её.
- Используйте **Synchronize** на сервере для всех его подключений. Запланированное
  действие также отзывает активный доступ архивированных сотрудников и связанных пользователей.
- Запросы Headscale не входят в транзакцию базы Odoo. Операция с ошибкой могла частично
  изменить удалённое состояние. Восстановите сервис и повторите: полный отзыв заново
  читает удалённые ключи и устройства, включая отсутствующие в локальном кеше.
- Архивирование сотрудника или связанного пользователя завершается ошибкой, если
  отзыв не удался. Устраните ошибку Headscale и повторите архивирование.
- Замените API-токен в окружении Odoo до истечения срока и проверьте через
  **Test connection**. Не сохраняйте API-токены и команды подключения в Git и отчётах.

## Секреты и границы доступа

Ключи подключения одноразовые и создают постоянные устройства. Срок действия ключа
ограничивает регистрацию, а не длительность сеанса. Сделайте ключ недействительным,
чтобы запретить регистрацию; отзовите устройство или весь доступ, чтобы удалить
существующие VPN-подключения.

Диалог подключения хранит команду с секретом во временной записи со сроком жизни
один час; удаление выполняет очистка временных записей Odoo. Закрытие диалога не
удаляет запись немедленно. Постоянная история ключей хранит идентификаторы и статусы,
но не секреты. Содержимое ответов HTTP с ошибками скрывается.

Политика VPN и шлюз определяют доступные сервисы. Аутентификация Odoo остаётся
обязательной, а отзыв не закрывает публичный маршрут Odoo. Для независимых
клонированных окружений используйте отдельный сервер Headscale и конфигурацию API,
чтобы не менять исходную сеть.

## Развёртывание сервисов в Oduflow

Используйте [примеры конфигурации сервисов](https://github.com/oduflow/oduflow-client-addons/tree/19.0-headscale/addons/oduscale/deploy)
как основу. Они содержат значения демонстрационного стенда: сначала выберите окружение,
имена сервисов, публичный домен управляющего сервера, префиксы VPN и домен DNS.
Фактические значения, аргументы инструментов, версии образов и результаты записывайте в
[журнал развёртываний](https://github.com/oduflow/oduflow-client-addons/tree/19.0-headscale/log).
Журнал содержит исторические наблюдения, а не актуальную опись окружений.

1. Опубликуйте выбранную ветку Git и вызовите `create_environment` с репозиторием,
   веткой, именем окружения, `odoo_image="odoo:16.0"` и `template_name="none"`
   для новой базы. В существующем окружении сохраните базу данных.
   Убедитесь, что `/mnt/extra-addons/addons` входит в путь дополнений. Используйте `pull_and_apply`
   с `install="oduscale"` для первой установки или `upgrade="oduscale"`
   для обновления модуля. Включите поток cron в `.oduflow/odoo.conf`.
2. Выберите и запишите конкретные версии образов Headscale и Tailscale. Создайте четыре
   тома через `create_volume`: конфигурацию Headscale, данные Headscale, состояние
   шлюза и конфигурацию шлюза. Для независимых установок используйте разные имена.
3. Адаптируйте `addons/oduscale/deploy/headscale/config.yaml`: задайте публичный HTTPS-адрес сервера,
   префиксы VPN и домен MagicDNS. Адаптируйте `addons/oduscale/deploy/headscale/policy.hujson`: пользователь
   шлюза владеет `tag:odoo`, а участники имеют доступ к этому тегу на порту 80. Адаптируйте
   `addons/oduscale/deploy/gateway/serve.json` для перенаправления порта 80 в контейнер Odoo на порт 8069.
   Через `write_file_in_volume` поместите `config.yaml` и `policy.hujson` в корень
   тома конфигурации Headscale, а `serve.json` — в корень тома
   конфигурации шлюза.
4. Вызовите `create_service` для Headscale с `command="serve"`. Подключите конфигурацию
   в `/etc/headscale:ro`, а данные в `/var/lib/headscale`. Опубликуйте только `/health`,
   `/key`, `/ts2021`, `/register`, `/auth`, `/oidc/callback`, `/verify` и
   `/machine/ping-response` на порту 8080. Не публикуйте общий маршрут или
   `/api/v1`. Odoo должен обращаться к API по внутреннему имени хоста сервиса.
5. Через `run_service_command` с `shell=false` создайте пользователя шлюза, если его
   нет, выпустите API-ключ, получите ID пользователя шлюза из списка пользователей
   и выпустите ключ предварительной авторизации шлюза с тегом `tag:odoo`. Подставьте пользователя и ID шлюза:

   ```text
   headscale users create <gateway-user>
   headscale apikeys create --expiration 2160h
   headscale users list -o json
   headscale preauthkeys create --user <gateway-user-id> --expiration 1h --tags tag:odoo -o json
   ```

   Поместите API-ключ в переменную окружения Odoo `ODUSCALE_API_KEY` через
   `update_environment`, сохранив остальные переменные. Запишите срок действия, но не
   значение. До истечения срока выпустите замену, обновите переменную, проверьте
   **Test connection** и отзовите старый ключ через `headscale apikeys expire`.
6. Вызовите `create_service` для шлюза Tailscale. Подключите состояние в `/var/lib/tailscale`,
   а конфигурацию в `/config:ro`. В демо используется `port=65535` без слушающего процесса,
   чтобы не публиковать VPN-перенаправление наружу. Задайте следующие переменные,
   подставив одноразовый ключ и публичный адрес управляющего сервера:

   ```text
   TS_AUTHKEY=<single-use-gateway-key>
   TS_AUTH_ONCE=true
   TS_STATE_DIR=/var/lib/tailscale
   TS_USERSPACE=true
   TS_HOSTNAME=odoo
   TS_EXTRA_ARGS=--login-server=<public-headscale-https-url> --accept-dns=false
   TS_SERVE_CONFIG=/config/serve.json
   ```

   Этот режим не требует привилегированного контейнера, `NET_ADMIN` или сети хоста.
   Теги берутся из ключа; не добавляйте `--advertise-tags`. После регистрации удалите
   `TS_AUTHKEY` через `update_service`, сохранив остальные настройки. Идентичность
   шлюза остаётся в томе состояния.
7. Настройте сервер Headscale в Odoo, как описано выше: внутренний API URL,
   публичный Login URL и Odoo URL в VPN. Выполните **Test connection**, затем по
   [руководству пользователя](user_guide.md) подключите временное устройство, синхронизируйте его,
   откройте Odoo через VPN и проверьте отзыв доступа. Убедитесь, что публичный `/api/v1/user`
   недоступен, а `/health` работает. Запишите фактические результаты и удалите тестовые
   устройства и ключи. При необходимости запустите простаивающее окружение через `start_environment`.

## Маршрутизация шлюза и резервное копирование

Пример шлюза перенаправляет TCP-порт 80 через зашифрованную VPN на порт Odoo
8069. При `workers=0` это также передаёт websocket-трафик. Несколько рабочих процессов
требуют внутреннего HTTP-прокси, направляющего `/websocket` на порт gevent.
Для доступа только через VPN подготовьте и проверьте доступ администратора
через VPN, прежде чем закрывать публичный маршрут Odoo на входном прокси.

В примере Headscale использует SQLite с WAL в постоянном томе данных;
отдельный сервис PostgreSQL не нужен. Копируйте SQLite через API резервного копирования
или при остановленном Headscale; сохраняйте также приватные ключи и конфигурацию.
Копируйте состояние и конфигурацию шлюза, а также базу данных и файловое хранилище Odoo.
Записывайте ссылки на копии и шаги восстановления до изменения сервисов; не помещайте
приватные ключи или учётные данные резервных копий в журнал. Для независимых клонов
Odoo используйте отдельный Headscale, чтобы их действия не меняли исходную VPN.

## Совместимость с Odoo 16

Для новой установки на Odoo 16 используйте ветку `16.0`. Установите модуль из `addons` вместе с объявленными зависимостями. Эта ветка не предназначена для понижения версии существующей базы Odoo.
